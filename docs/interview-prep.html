Part A — Understand the project

1. The 2-minute pitch

Say this in about two minutes. Practise it until you don't need the page.

  1. Problem. Students split rent, food orders and trips all the time. Splitwise's free tier limits how many expenses you can add per day and puts receipt scanning, currency conversion, search and default splits behind Pro (₹149/month in India).
  2. Who it's for. Flatmates, trip groups and hostel friends in India, mostly on phones, paying each other over UPI. And the evaluator on a laptop.
  3. What it is. Quits is a free, mobile-first web app (installable as a PWA). There are no accounts: a group is a link with a 128-bit random token, and on each device you pick who you are once.
  4. What makes it stand out:
    • Fewest payments, provably. Settle says "3 payments instead of 10". Under "How?", the exact minimum comes from a bitmask dynamic program over zero-sum subsets, compared with greedy and naive.
    • UPI QR settle-up. Each payment has a QR with the payee and amount filled in. It's QR-first because I tested on a real phone and GPay, PhonePe and Paytm all blocked upi://pay links opened from a website.
    • Itemized receipts. Gemini reads the bill photo, each person taps what they had, and tax and service are shared in proportion. If the numbers don't add up to the printed total within ₹1, it's flagged.
    • Type to add in English or Hinglish: "maine 450 diye auto ke, sab mein" fills the form, and nothing is saved until you tap Save.
    • Exact money. Everything is integer paise, with a largest-remainder rule, so every group's balances sum to exactly zero.
  5. It's measured and honest. Two evaluations are published on the About page: a receipt eval (n = 5) and a type-to-add eval (n = 30), with small-sample warnings and answer rate shown separately from accuracy.
  6. How it was built. Spec-first, with Claude Code. SPEC.md has 73 EARS requirements, 60 pass/fail acceptance criteria and 41 decisions, plus a changelog from v0.1 to v1.7. PLAN.md records the evidence for every criterion: 58 of 60 pass. The two failures are Should-level accuracy targets, and I can explain why.
  7. Try it: https://quits-go.vercel.app; evaluators use https://quits-go.vercel.app/demo.

2. Architecture and request flows

Layers, from the outside in

  • Browser. React client components render the UI. Per-device state lives in localStorage: the member you picked (quits:me:{token}), the theme (quits:theme) and "Your groups" (quits:recent). The browser never calls Supabase or Gemini, and holds no keys.
  • Next.js on Vercel. Pages are Server Components. Mutations are Server Actions in app/actions.ts, thin wrappers that call server/*. Uploads and long AI calls go through Route Handlers.
  • server/*. Each operation validates input with zod, resolves the group from the URL token (findGroupByToken → isValidToken), checks that every member id belongs to that group, then calls a Postgres function through rpc(). server/db.ts starts with import "server-only" and uses the secret key.
  • lib/*. Pure TypeScript with no React, Next, Supabase or fetch imports, so it can be unit-tested directly. All the money, split, simplify, receipt, currency, NL-parsing, UPI and share logic lives here.
  • Postgres. 14 tables, RLS on with no policies, and table privileges revoked from the browser roles. Every multi-row write is one PL/pgSQL function, which makes it a single transaction, and the functions re-check invariants.

Flow 1: adding an expense

  1. Client: expense-form.tsx calls the Server Action createExpenseAction(token, input, actor). actor is the member id stored on this device.
  2. Action: run() wraps server/expenses.ts › createExpense, turns AppErrors into friendly messages, and calls refresh() on success.
  3. Server:
    • requireGroup(token), then loadMembers.
    • prepareExpense: zod parse; assertMembersBelong; resolveRate (identity, cached rate, Frankfurter, or a manual rate); buildExpenseAmounts in lib/splits.ts, which splits, validates payers, converts to the base currency and asserts the invariants.
  4. Database: rpc("create_expense"). In one transaction the function checks the group exists, runs _assert_members, inserts the expense, writes the payer and split rows (_write_expense_rows), re-checks Σpayers = Σsplits = total in both currencies (_check_expense_invariants, otherwise INVARIANT_VIOLATION), and logs activity.
  5. Client update: refresh() re-renders the Server Components. readGroup recomputes balances, the plan and the naive count from the database, and checks Σbalances = 0 (otherwise a 500).

Flow 2: scanning a receipt

  1. Client: scanner.tsx gets a camera photo, picked file, paste or drop. app/_lib/compress.ts redraws it on a canvas (longest edge ≤ 2000 px, JPEG quality 0.85 down to 0.5, then smaller) until it is ≤ 1,000,000 bytes, then POSTs it as multipart.
  2. Route /api/g/[token]/receipts/extract:
    • group from token, otherwise 404;
    • body larger than 1,048,576 bytes → 413;
    • magic-byte sniff for JPEG, PNG or WebP (server/image.ts), otherwise 415;
    • bumpScanLimits: 30 per group and 300 per app per IST day, otherwise 429.
  3. AI: extractReceipt calls geminiReceiptClient (image + RECEIPT_PROMPT + RECEIPT_JSON_SCHEMA, temperature 0) inside a 25 s timeout. parseModelReceipt validates the output with zod and converts major units to paise.
  4. Database: createReceiptDraft stores the extracted data. The image itself is never stored or logged.
  5. Client update: the browser opens /g/{token}/receipts/{id}. In the editor, every field is editable, the mismatch banner shows when |diff| > ₹1, and members tap their items. finalize_receipt creates one itemized expense for the printed total.

Flow 3: type to add

  1. Client: type-it.tsx POSTs { text, me } to /api/g/[token]/expenses/parse.
  2. Route: parseExpenseText = createParseHandler(deps) in server/nl-handler.ts. Its dependencies are injected, so the route is unit-tested with a mocked Gemini.
  3. Handler:
    • group or me not found → 404; bad body → 400;
    • bumpLimits: 50 per group plus the shared 300 per app per day, otherwise 429;
    • Gemini with NL_PROMPT + NL_JSON_SCHEMA, one retry after about 1 s on an error, all inside a single 20 s deadline;
    • parseNlModel (zod), then resolveNl, which matches names and validates every field deterministically.
  4. Response: { prefill, flags }. The form fills in and highlights blank or unclear fields. Nothing is written except the rate-limit counters.
  5. Failure: 502 with reason (timeout, model_error or invalid_output) and Gemini's HTTP status. The UI shows "Couldn't read that — try again".

4. Data model and key algorithms (simply)

All money columns are bigint amounts in minor units (paise for INR). Soft delete means setting a deleted_at timestamp. Every table has RLS on with no policies.

Relations: everything hangs off groups with on delete cascade. The member foreign keys on payers, splits and settlements are DEFERRABLE INITIALLY DEFERRED, so deleting a whole group can cascade, while deleting a referenced member on its own still fails (see the debugging stories).

The three algorithms, simply

  • Splitting money fairly: work in paise, give each person the rounded-down share, then hand out the leftover paise one at a time to whoever lost the most in rounding (the largest remainder). Ties go to the earlier member. Example: ₹100 among A, B and C → 3334, 3333, 3333 paise.
  • Balances: balance = what you paid − what you owe + settlements you sent − settlements you received. They always sum to 0.
  • Fewest payments: find the largest number of separate groups of people whose balances cancel to zero. If n people are owed or owe, and k groups cancel out, you need exactly n − k payments. Demo: Aarav +4,000, Priya +3,000, Rohan +3,000, Sneha −6,000, Kabir −4,000. {Aarav, Kabir} and {Priya, Rohan, Sneha} each cancel, so 5 − 2 = 3 payments; greedy takes 4. 6. Spec-driven development (SDD)

  • SPEC.md is the contract: goal, users and scenarios, constraints, data model and interfaces, then EARS requirements. EARS stands for "Easy Approach to Requirements Syntax": WHEN trigger THE SYSTEM SHALL response, IF unwanted condition THEN …, WHILE state …. Each requirement is Must or Should. Then come pass/fail acceptance criteria, each with a test type (Unit, Script, Deploy, Phone, Desktop), and the deliverables, non-goals, risks (K1–K15), decisions (D-1 to D-41) and a changelog.
  • PLAN.md breaks the build into phases (1–12). Each task is tagged AUTO (Claude Code does it) or HUMAN (I do it: deploys, env vars, phone checks, eval data). It also has the rules for the autonomous build and an AC status table, where every row needs evidence (a test name, a command and its result, or a live check).
  • The rules that made it work:
    • "Fix the spec, not the code": if a requirement turned out to be wrong or impossible, stop and propose the SPEC change. Never weaken a test.
    • One commit per phase.
    • Never push from the agent.
    • Never read .env.local.
    • Never edit an applied migration.
  • The final count: 73 requirements (49 Must, 24 Should) and 60 ACs. 58 pass; AC-25 and AC-52 fail, and both are Should-level accuracy targets.

Four spec changes worth telling as stories

  1. v0.5, QR-first settle-up (D-18). The Phase 1 phone test (P1-8) showed upi://pay links blocked in GPay, PhonePe and Paytm when opened from a website, while QR scans worked. The spec changed before any settle UI was built: the QR became the Must path, and the deep link a best-effort Should labelled "May be blocked by some UPI apps".
  2. v0.4, SC-3 (R17 currency weights). AC-6 expects an equal USD split to stay equal in INR. Weighting by rounded cents gave 34384/34301/34301; weighting by exact proportions gives 34329/34329/34328. The wording changed to "exact proportions", and the code already did that.
  3. v1.0, type-to-add reliability (D-28 to D-30). I investigated eval failures with a 60-call probe: every error was HTTP 503 "high demand", some arriving after 12 s, so a 15 s limit left the retry no time. The limit became 20 s with a 1 s wait before the retry, a "Try again" button was added, and real status codes are recorded. A fallback model was rejected.
  4. v1.1, eval set size (D-33). R37 originally asked for 10–15 receipts. With 5 real, hand-checked receipts, I changed R37 to "at least 5" and required "n = 5, small sample" wherever the numbers appear, rather than padding the set with weak data.

Every version is in the changelog deep dive below, with the reason for each.

7. Testing, CI and evaluation

  • Unit tests (Vitest), 162 tests in 16 files, mostly on the pure lib/ modules:
    • Property test (AC-5): a seeded PRNG makes 1,000 random groups (2–12 members, 1–40 expenses, every split type, multiple payers, currencies and settlements). For each one, every expense's payers and splits sum to its total in both currencies, and Σbalances = 0.
    • Brute force (AC-11): for 300 random cases with n ≤ 8, the optimal count equals an exhaustive search over all set partitions, and is ≤ greedy.
    • Exact strings: UPI link (AC-13), share messages (AC-54), the Settle headline (AC-57).
    • Mocked AI: the parse route with a fake Gemini (timeouts, 503 retries, invalid output); receipt extraction timeouts.
    • Design: contrast of every theme token pair (≥ 4.5:1), avatar and category colours, QR colours and margin.
  • DB integration tests, 24 tests in 4 files (tests/db/), against the real Supabase:
    • security: no table without RLS; set role anon → permission denied on all 14 tables; anon can't run RPCs; cross-group ids → 404;
    • the ledger and receipt RPCs;
    • features: live Frankfurter v2 (AC-8), search counts, recurring generation, demo reset.
    Test groups use a __test__ prefix, with a cleanup script. These tests skip without SUPABASE_DB_URL.
  • CI: ci.yml on every push (ubuntu-24.04, Node from .nvmrc): npm ci, lint, typecheck, unit tests. DB tests are not run in CI because they need the DB URL.
  • End-to-end: there is no committed E2E suite. UI checks were scripted headless-Chrome runs over the DevTools protocol, plus my own live checks on production and an Android phone, recorded as evidence in PLAN.md.
    • Example: the last audit was 26 checks × dark/light × 360/1440 px = 104 runs. It covered no horizontal scroll, no wrapped button labels, tap targets ≥ 44 px, text contrast at AA, no truncation except users' own text, the QR on white, and the home-page order.
    • Committing those as Playwright tests is in "what I'd do next".
  • Evaluations (details in the deep dive):
    • npm run eval: 5 receipts → item precision, recall and F1, total accuracy, reconciliation rate, latency.
    • npm run eval:nl: 30 sentences → field accuracy, exact match, correct abstention.
    • Both report the answer rate separately from the accuracy when answered, keep every run, and label which runs are not blind.

8. Deployment, environments, secrets, security and privacy

  • Environments:
    • Local: npm run dev, or next start for audits.
    • Production: Vercel, built from main on every push. The agent never pushed; I pushed.
    • Database: one Supabase free project, with migrations applied by npm run db:push using SUPABASE_DB_URL (the session pooler string). That URL lives only on my machine and never in Vercel.
  • Secrets: SUPABASE_URL, SUPABASE_SECRET_KEY, GEMINI_API_KEY (plus SUPABASE_DB_URL locally) live in .env.local (gitignored) and in Vercel env vars. .env.example lists names only. No NEXT_PUBLIC_* variable holds a secret.
    • .claude/settings.json denies the agent reading .env.local.
    • Scripts load the file themselves with node --env-file-if-exists=.env.local.
    • Checks: .next/static grep for key patterns finds nothing; git log -p grep finds nothing (AC-42).
  • Security model, stated plainly: anyone with a group's link can view and edit it. The 128-bit token is the capability, and the member you pick is self-declared, not a login. Mitigations:
    • Referrer-Policy: no-referrer on every route; X-Robots-Tag: noindex, nofollow on /g/*;
    • soft delete plus an activity log with Restore;
    • every server operation resolves the group from the token and rejects ids from other groups (AC-43);
    • uploads are size-limited and sniffed by magic bytes; daily rate limits on AI calls.
  • Database lockdown: RLS is on with no policies, privileges are revoked from anon and authenticated, and RPCs are executable by service_role only.
    • Verified: REST with the publishable key → 42501 on all 14 tables (AC-41).
    • Production network log: 0 requests to *.supabase.co or generativelanguage.googleapis.com (AC-42).
  • Privacy:
    • Receipt images are never stored. The scan screen says the photo goes to Google Gemini, whose free tier may use inputs.
    • No phone numbers are stored; reminders open WhatsApp, where the user picks the contact.
    • "Your groups" stays in the device's localStorage, and listed links aren't prefetched.
    • The own-UPI-QR feature decodes in the browser and sends only the ID and name.
  • Keep-alive: Supabase free projects pause after about 7 idle days, so a GitHub Action calls /api/health daily.
    • AC-44: the production build, started locally with SUPABASE_URL=https://invalid.example for that one process only, returns 503 {"ok":false}. The normal environment returns 200 {"ok":true}.

9. Debugging stories (real ones)

Each one follows the same arc: symptom → how it was found → root cause → fix → how the fix was proven.

  1. UPI deep links blocked.
    • Symptom: opening upi://pay from the site failed in all three apps. GPay showed a misleading "exceeded bank limit" error at ₹1.
    • Found by: the Phase 1 phone test (P1-8), deliberately run before any settle UI existed.
    • Fix: SPEC v0.5 made settle-up QR-first. Scanning the QR from a laptop screen and from a gallery screenshot worked, with the payee and amount filled in.
  2. Postgres rejected the UPI-ID check.
    • Symptom: any non-null UPI ID raised error 2201B.
    • Root cause: Postgres regex bounds max out at 255, and the spec's rule was {2,256}.
    • Fix: new migration …000400 keeps the same rule using char_length(split_part(upi_id,'@',1)) between 2 and 256. The applied migration was not edited.
  3. Deleting a group failed.
    • Symptom: demo reset and test cleanup failed.
    • Root cause: the member foreign keys were RESTRICT, which is checked immediately. Switching to NO ACTION (…000300) still fired mid-cascade.
    • Fix: DEFERRABLE INITIALLY DEFERRED (…000400), checked at commit after the cascade has removed the rows. Deleting a still-referenced member on its own still fails.
  4. Currency weights (SC-3).
    • Symptom: an equal USD split stopped being equal in INR (34384/34301/34301).
    • Root cause: the converted total was allocated by the rounded cent shares.
    • Fix: allocate by the split's own exact weights (1 per person for equal, basis points, shares). Gives 34329/34329/34328 (AC-6).
  5. BUG-1: names squeezed to zero width.
    • Symptom: in the Exact, % and Shares modes, split rows showed no member names.
    • Root cause: the input had both w-full and w-28. Tailwind decides by stylesheet order, not class order, so w-full won.
    • Fix: inputBase/inputFixed() with exactly one width, a presentational SplitRows component, and a unit test that every row renders its name with no competing width classes.
  6. Type-to-add eval failures.
    • Symptom: runs 1–2 had sentences with no answer.
    • Investigation: classified every failure and ran a 60-call probe.
      • All errors were HTTP 503 "high demand" (no 429s), some after 12 s.
      • No answered call took more than 12.4 s.
      • Thinking was not the cause: 0 thinking tokens either way, and thinkingBudget: 0 is rejected.
    • Fix: the limit went from 15 s to 20 s with a 1 s wait before the one retry. Statuses are recorded, and the UI got "Try again" (D-28 to D-30).
  7. Two receipts that wouldn't reconcile.
    • Symptom: in run 1, r01 and r04 had the right totals but didn't reconcile, and the run had saved no predictions to explain why.
    • Diagnosis: D-32 made the eval save every prediction. Run 2 then showed:
      • r01: an add-on line ("Dimsums Extra … = 150") read as a separate item, so ₹150 was counted twice;
      • r04: the ₹14.99 platform fee was dropped.
    • Fix: two prompt rules (D-34), with unit tests. Run 3 is labelled not blind for these two receipts.
  8. The demo's balances broke.

10. Limitations, accepted trade-offs and what's next

Known limitations

  • No accounts: the link is the key. Identity is self-declared, and "Your groups" is per device.
  • Last write wins on concurrent edits, with no conflict detection. The activity log shows both edits, and deletes can be restored.
  • No real-time updates: other people's changes appear on refresh.
  • No editing after the fact: itemized expenses can't be edited once finalized (D-19), and recurring rules can be paused or stopped but not edited (D-20; R46 partially met).
  • AI on the free tier: Gemini is sometimes slow or returns 503 at busy times, and has daily limits. Both evals are small (n = 5 and n = 30).
  • Two failed Should targets:
    • AC-25 (receipts): F1 0.452 overall, because one receipt timed out at 25 s; 1.00 on the answered receipts.
    • AC-52 (type-to-add): amount and exact match 76.7%, because 6 of 30 got no answer; 95.8% on the answered sentences.
  • Above 18 people with nonzero balances, the plan is greedy, not proven optimal.

What I would build next

  1. Commit the headless audits as a Playwright E2E suite running in CI against a preview deployment.
  2. Larger, more varied eval sets (more receipts, more Hinglish), with a held-out test split so prompt changes stay blind.
  3. Optional sign-in (for example a magic link) to sync "Your groups" across devices and give real per-member identity, while keeping link-only groups.
  4. Editable itemized expenses and recurring rules.
  5. Faster reads for big groups: cache or materialize balances instead of recomputing from all expenses on each view.
  6. Live updates via server-sent events or polling. The browser must still never talk to Supabase directly.

Deep dives

D1. Minimum payments: naive vs greedy vs exact bitmask DP

This is the question you will most likely be grilled on. Know the definitions, the proof and the demo numbers by heart.

Setup

From the ledger, each member has a balance in paise: paid − owed + settlements sent − settlements received. Balances sum to exactly 0. Positive means the group owes you; negative means you owe. People with a zero balance are dropped, which leaves n nonzero balances. All three methods live in lib/simplify.ts.

1. Naive count (R21, D-8): what you'd pay without simplifying

For every expense, each participant owes each payer a share in proportion to what the payer paid, allocated with the largest-remainder rule. Settlements reduce the pair. Then count the pairs of members with a nonzero net amount. AC-10 example: A pays ₹300 and B pays ₹600, each split equally among A, B, C.

  • From A's expense: B owes A ₹100 and C owes A ₹100.
  • From B's expense: A owes B ₹200 and C owes B ₹200.
  • Net per pair: A owes B ₹100, C owes A ₹100, C owes B ₹200. Three nonzero pairs, so naive = 3.
  • Balances: A 0, B +300, C −300. So greedy and optimal are both 1: C→B ₹300.

2. Greedy (R20): simple, not always optimal

loop:
  debtor   = most negative balance   (ties: earlier member)
  creditor = most positive balance   (ties: earlier member)
  if none: stop
  x = min(|debtor|, creditor);  debtor pays creditor x

Each step zeroes at least one person, so it uses at most n − 1 payments. AC-9: A +400, B +300, C +300, D −600, E −400 (₹).

  1. D (−600) pays A (+400) ₹400 → D −200, A 0.
  2. E (−400) pays B ₹300 (B and C tie at +300; B wins by member order) → E −100, B 0.
  3. D (−200) pays C (+300) ₹200 → D 0, C +100.
  4. E (−100) pays C ₹100 → done. 4 payments.

3. Exact minimum (R19): n − k

Claim: the minimum number of payments is n − k, where k is the largest number of disjoint subsets whose balances each sum to zero (together the subsets cover all n people).

Lower bound proof. Draw the people as nodes and each payment as an edge. Money only moves along edges, so every connected component must net to zero. The components therefore split the n people into zero-sum groups, so there are at most k of them. A connected component with m nodes needs at least m − 1 edges. Total payments ≥ Σ(mᵢ − 1) = n − (number of components) ≥ n − k.

Upper bound (achievable). Take a partition into k zero-sum groups and run greedy inside each group. Within a group of size m, every greedy payment zeroes at least one person, and the last payment zeroes two. So greedy uses at most m − 1 payments per group, and n − k in total. The bounds meet, so the optimum is exactly n − k.

On AC-9: {A, E} = 400 − 400 = 0 and {B, C, D} = 300 + 300 − 600 = 0, so k = 2 and the minimum is 5 − 2 = 3: E→A 400, D→B 300, D→C 300.

Finding k: dynamic programming over subsets (maxZeroSumPartition)

for mask in 1 .. 2^n − 1:
  sums[mask] = sums[mask without its lowest bit] + value[lowest bit]
  dp[mask]   = max over j in mask of dp[mask without j]
               + (sums[mask] == 0 ? 1 : 0)
k = dp[full mask]

Why this works. Imagine adding people one at a time in some order. Every time the running total returns to zero, one zero-sum group has just closed. So the number of zero-sum groups in a partition equals the number of zero-sum prefixes in a suitable ordering. dp[mask] is the best number of zero-sum prefixes for the people in mask, maximised over which person came last.

Recovering the actual groups, deterministically: start from the full mask and repeatedly remove the lowest index that keeps dp optimal. Each time the remaining mask sums to zero, a group ends. Greedy then runs inside each group in member order. The same input always gives the same plan (AC-12: two runs are deep-equal).

Cost: O(n · 2ⁿ) time and O(2ⁿ) memory. At n = 18 that is 2¹⁸ = 262,144 states × 18 ≈ 4.7 million steps, in a Float64Array (sums) and an Int32Array (dp). AC-12 requires 18 random balances to solve in under 2 s, and 19 nonzero balances to fall back to greedy (algorithm = "greedy", optimalCount = null, shown as "not computed (> 18 people)").

Why not always exact? Minimising the number of payments is NP-hard in general. Finding the maximum number of zero-sum groups contains the Partition / Subset-Sum problem. So exponential time is unavoidable for an exact answer, and the cap keeps it fast for student groups.

How it's tested

  • AC-9: the exact greedy and optimal lists, and applying either one zeroes every balance (applyPayments).
  • AC-11: all-zero balances → 0 payments; {+x, −x} → 1; and for 300 random cases with n ≤ 8, the DP equals a brute force over all set partitions and is ≤ greedy.
  • AC-12: the 18-person timing and the 19-person fallback.
  • AC-36: the demo seed's balances give greedy 4 and optimal 3. The demo's naive count is 10, which is why Settle says "3 payments instead of 10".

How it's shown (R22, D-38)

The main view says "3 payments instead of 10" with a "Simplified" badge (paymentHeadline). "How?" shows Naive 10 · Greedy 4 · Optimal 3, plus one sentence: Quits nets everyone's balance, then finds the smallest set of payments by grouping people whose debts cancel out exactly.

D2. Money: integer paise, the largest-remainder rule and currencies

Why integers

In binary floating point, 0.1 + 0.2 !== 0.3. A ledger has to prove Σ payers = Σ splits = total and Σ balances = 0 exactly. So every amount is a safe integer number of minor units (assertMinor). Every product such as total × weight is computed in BigInt (allocate), so it can't overflow either. The database stores bigint.

The largest-remainder rule (R13, lib/money.ts › allocate)

  1. Each person gets floor(total × wᵢ / Σw).
  2. The leftover units (total − Σ floors) go one at a time to the largest remainders (total × wᵢ mod Σw).
  3. Ties go to the earlier entry. Callers pass people in member order (display_order), so the result is deterministic.
  4. A negative total is allocated as |total| and then negated. This is used for receipt remainders when the discount is bigger than tax.

Validating splits (R9)

  • Exact amounts must sum to the total. Otherwise the error is EXACT_MISMATCH with the difference (AC-3: 9999 of 10000 → difference 1).
  • Percentages are basis points and must sum to 10000 (99.99% is rejected).
  • Shares must not all be zero.
  • Payers must be ≥ 0, with at least one paying, and sum exactly to the total.

Currencies (R15–R18)

  • Currencies and exponents: there are 21 supported currencies, each with its exponent (INR 2, JPY 0, …). The base currency is locked after the first expense (D-1).
  • Rate lookup:
    • The base currency uses identity.
    • Otherwise the fx_rates cache is checked, then Frankfurter v2 /v2/rate/{BASE}/{QUOTE}?date= is called with a 5 s timeout.
    • Future dates request the latest rate and aren't cached. Weekends return a blended rate for that date.
    • On failure with nothing cached → RATE_UNAVAILABLE, and the form asks for a manual rate (fx_source = manual).
  • Conversion (R17): convert the total once, base = round_half_up(amount × rate × 10^(exp_base − exp_src)), using exact decimal maths. Then allocate the converted total across payers and splits by their exact original proportions (SC-3).
    • AC-6: USD 12.34 at "83.4567" → 102986 paise, and an equal three-way split gives [34329, 34329, 34328]. Weighting by the rounded cents (412/411/411) would have given [34384, 34301, 34301], so the split would no longer be equal.
    • Other AC-6 cases: THB 10.05 at 2.35 → exactly 2362 (half-up of 2361.75); JPY 1000 at 0.5612 → 56120.
  • Stored for good: the rate and its date are stored on the expense. Editing only the description keeps the rate; changing the date re-fetches it (AC-8).
  • Display: Intl.NumberFormat("en-IN") is given a decimal string (₹1,23,456.78), so formatting never goes through a float.

D3. The Gemini receipt pipeline

  1. Capture (R27–R29): camera, picked file, Ctrl+V paste or drag-and-drop, then browser compression: longest edge ≤ 2000 px, JPEG quality 0.85 down to 0.5, then smaller, until ≤ 1,000,000 bytes. EXIF orientation is applied, and transparency becomes white.
  2. Guards before any AI call (R30): group from token (404) → size > 1,048,576 bytes (413) → magic bytes JPEG, PNG or WebP (415) → daily limits, 30 per group and 300 per app (429).
  3. Model call (R31): geminiReceiptClient sends the image as inline data plus RECEIPT_PROMPT, with responseMimeType: application/json, responseJsonSchema: RECEIPT_JSON_SCHEMA and temperature 0, inside a 25 s timeout (extractReceipt; the route has maxDuration = 60). The image is never stored or logged.
  4. Output contract (SPEC §4.3): merchant, date, currency, items [{name, quantity, amount = line total}], tax, service_charge, tip, discount, round_off and total, all in major units. Prompt rules include:
    • tax = the sum of all tax lines (CGST + SGST …);
    • tax, totals and discount lines are never items;
    • D-34: add-on lines under an item belong inside that item's amount;
    • D-34: platform, packaging, convenience and delivery fees go in service_charge.
  5. Validation (parseModelReceipt): zod requires an items array and non-negative amounts (except round-off). Major units are converted to paise half-up (AC-19: 12.5 → 1250). Any failure gives EXTRACT_FAILED with reason timeout, model_error or invalid_output; the UI shows "Couldn't read this receipt" with Retry or "Enter items manually" (R32).
  6. Review (R33): every value is editable. diff = total − (Σitems + tax + service + tip − discount + round_off), and if |diff| > ₹1 a mismatch banner appears (AC-17: diff 150 is flagged, 100 is not, 101 is).
  7. Claim (R34, R36): on each item, tap who had it (one or more people). Each item is split equally among them with the largest-remainder rule. Drafts can be opened on other devices.
  8. Finalize (R35, D-3): the expense amount is the printed total. The remainder (total − Σitems, covering tax, service, discount, round-off and any unexplained difference) is allocated in proportion to each person's item subtotal (allocateItemized).
    • AC-18: Pizza ₹400 (A, B), Coke ₹100 (A), Pasta ₹300 (C) → subtotals 30000 / 20000 / 30000. With printed total ₹845, the remainder 4500 is allocated as [1688, 1125, 1687].
    • finalize_receipt writes the itemized expense atomically. Itemized expenses can't be edited afterwards (D-19).

D4. The type-to-add pipeline

  1. Input (R61): the "Type it" box takes up to 300 characters. You can dictate with the phone keyboard's microphone; there is no speech-recognition code. On a new expense, the cursor starts there (D-25).
  2. Route guards: group and me must exist (404); text must be 1–300 characters (400); limits are 50 per group per IST day plus the shared app-wide 300 (429: "Daily limit reached — fill in the form").
  3. Prompt (NL_PROMPT): use only what the sentence says, and null if something isn't stated; copy names exactly as written; "me" for the speaker; D-21 rules on who takes part; split types; category from the fixed list; dates resolved from "today". The user turn is built by nlUserText: the members' first names, the base currency, today with its weekday, and the sentence.
  4. Call: geminiTextJson with NL_JSON_SCHEMA at temperature 0. On a model error the route waits about 1 s and retries once, all inside one 20 s deadline (D-29).
  5. Deterministic post-processing (resolveNl): the model only reads the sentence; code decides everything else.
    • Names match the full or first name, case-insensitively. No match → unknown; two matches → ambiguous. A member is never created.
    • Words meaning the current member (ME_WORDS: me, i, main, maine, mujhe, mera; D-24) and words meaning everyone (ALL_WORDS: everyone, everybody, all, all of us, sab, sabhi, sab log, hum sab; D-23) are matched in code.
    • Validated: the amount (> 0, ≤ 10,000,000); the currency (supported, otherwise the base); the date (not in the future, not older than a year); the category (from the list); and the split, using the same computeSplit as the form.
    • Anything invalid is left blank and flagged. If the same person appears twice in a split, the split is left blank (P3).
  6. Never saves (R64): the response is { prefill, flags }. The form fills in and highlights flagged fields, and only the user's Save writes anything.
  7. Failure UX (D-28): "Couldn't read that — try again", with a Try again button that resends the same text and a smaller "or fill in the form". After about 6 s the box says "Still reading… Gemini is busy".

D-21 in examples:

  • "Rahul paid 600 for pizza, split with Amit and me" → participants Rahul, Amit and me. The payer is included unless the text excludes them ("only for A and B").
  • An explicit list of shares or amounts per person is the complete split, so the payer is not added.
  • A "treat" means the payer is the only participant.

D6. The UPI deep-link failure and the QR-first pivot

  • The link format (R24, AC-13): upi://pay?pa=priya@okicici&pn=Priya%20S&am=450.50&cu=INR&tn=Quits%3A%20Goa%20Trip. pn and tn are URI-encoded, the @ in pa stays literal, the amount always has 2 decimals, and the note is cut to 50 characters (lib/upi.ts).
  • The risk was planned for. SPEC risk K1: UPI apps might block P2P deep links from websites. So Phase 1 had a throwaway /lab/upi page and a phone test, P1-8, before any settle UI was built.
  • Result, on a Samsung phone against the deployed app, 2026-10-16:
    • The upi://pay link opened from the website was blocked in GPay, PhonePe and Paytm. GPay showed a misleading "exceeded bank limit" error at ₹1.
    • A QR shown on a laptop and scanned by the phone worked, with payee and ₹1.00 filled in.
    • A QR screenshot scanned from the gallery also worked.
  • The pivot (SPEC v0.5, D-18):
    • Must: the QR is visible at every width, plus "Save QR image" (a PNG with payee, amount and UPI ID), "Show full screen" (for a second phone to scan), and "Copy UPI ID" with the amount in large text.
    • Should (R59): the link stays as a best-effort "Pay via UPI app", labelled "May be blocked by some UPI apps".
    • R25: Quits never handles money. A payment is recorded only on "Mark as paid", never automatically, and the old "Did it go through?" prompt was removed.
    • R26: a warning above ₹1,00,000, since UPI apps may limit single payments.
    • D-4: UPI actions appear only in INR groups.
  • R60 (Should): you can set your UPI ID from a screenshot of your own UPI QR. It is decoded in the browser (BarcodeDetector, otherwise jsQR), and only pa/pn are sent to the server.
  • Theming can never break scanning (D-39): the QR is a light island, #000000 on #ffffff with a 4-module quiet zone, on screen, full screen and in the saved image. AC-58 was checked on the phone in the dark theme.
  • Why it's a good story: I retired the riskiest assumption first, with a cheap real-device test, and changed the spec before writing the feature rather than after.

D7. Supabase RLS and server-only access

  • The threat: Supabase gives every project a public REST API. With an "anon" or "publishable" key, a browser could read tables directly. Quits has no user accounts, so per-user RLS policies would have nothing to check.
  • The design, in four layers:
    1. RLS is enabled on every table with no policies, so for the browser roles every row is invisible.
    2. revoke all on all tables … from anon, authenticated: no table privileges at all, so requests fail with 42501 permission denied rather than returning nothing.
    3. Every RPC function has revoke … from public, anon, authenticated and grant execute … to service_role.
    4. The only key the app uses is the secret (service-role) key, in server/db.ts, which starts with import "server-only" (importing it from client code fails the build). No NEXT_PUBLIC_* variable holds a key, so the browser has no Supabase key at all.
  • Authorization therefore lives in code and SQL, because the service role bypasses RLS:
    • every operation resolves the group from the URL token (findGroupByToken checks the token format first);
    • assertMembersBelong in TypeScript and _assert_members in SQL reject member ids from other groups, so AC-43 cross-group requests get 404 and nothing changes;
    • the device's "actor" member id is validated the same way (actorId).
  • Evidence:
    • AC-41: SQL finds 0 tables without RLS; set role anon → permission denied on all 14 tables; anon can't run RPCs. REST with the publishable key → 42501 on all 14 tables (checked by me on production).
    • AC-42: no key patterns in .next/static or the git history, and the production network log shows 0 requests to *.supabase.co or Gemini.
  • Trade-off: the server is the single gatekeeper, so a bug in an ownership check would matter. That's why the checks are duplicated in SQL and covered by DB tests.

Product and users 6

Q1★Give me your 2-minute pitch for Quits.

SayQuits is a free, mobile-first bill-splitting web app for Indian students, at quits-go.vercel.app. Splitwise's free tier limits daily expenses and paywalls receipt scanning, currency conversion and search. Quits makes those free and adds three things. First, UPI QR settle-up with the payee and amount filled in. Second, itemized receipts read by Gemini, where each person taps what they had. Third, provably minimal payments: Settle says "3 payments instead of 10". There are no accounts; a group is a 128-bit link. Money is integer paise, so balances always sum to zero. I built it spec-first with Claude Code: 73 EARS requirements and 60 acceptance criteria, of which 58 pass.

Likely follow-upWhat are the two that fail?

AC-25 and AC-52. Both are Should-level accuracy targets on small evals. The receipt F1 is 0.452 overall because one receipt timed out (1.00 when answered). Type-to-add amount and exact match are 76.7% because 6 of 30 sentences got no answer from Gemini (95.8% when answered).

Q2Who exactly is the user, and what problem do they have?

SayThree groups from the spec: flatmates (rent, Wi-Fi, electricity, food delivery), trip groups (sometimes with a foreign currency) and hostel friends (frequent small orders and restaurant bills). Their problem is tracking who owes whom without friction or paywalls, and then actually settling, which in India means UPI. A fourth user is the evaluator on a laptop, which is why there's a /demo link.

Likely follow-upDid you talk to any users?

The scenarios come from my own and friends' situations. Real use shaped the build: the five eval receipts are real bills, and I tested settle-up with my own UPI ID on my phone. A proper user study is future work.

Q3How is Quits different from Splitwise, Spliit or Tricount?

SaySplitwise's free tier caps expenses and puts scanning, conversion, search and default splits behind Pro (₹149/month in India). Spliit is free and open source, and Tricount is free with link-shared groups. Quits' edge is the combination: everything Pro unlocks is free, plus UPI QR settle-up with the amount filled in, itemized receipts with proportional tax, a provably minimal number of payments, type-to-add in Hinglish, and published accuracy numbers.

Likely follow-upIsn't 'free' just because you have no costs yet?

Yes, it runs entirely on free tiers: Vercel Hobby, Supabase free, Gemini free tier, Frankfurter and GitHub Actions. Daily AI limits protect the Gemini quota. At real scale, AI calls would cost money, which I discuss under scalability.

Q4Why no accounts?

SaySign-up friction kills group apps: one friend who won't create an account blocks the whole group. Quits uses a share link with a 128-bit random token, and on each device you pick your name once. Likely follow-upSo I could edit as someone else?

Yes. Identity is self-declared, not authentication. The activity log records which device-chosen member did what, and deletes are soft so they can be restored. Real per-member identity would need optional sign-in, which is on my future list.

Q7★What is spec-driven development, and how did you apply it?

SayWrite down what to build and how you'll prove it before building. SPEC.md has the goal, users and constraints, 73 requirements in EARS form tagged Must or Should, and 60 pass/fail acceptance criteria, each with a test type. Q8What is EARS? Show me one of your requirements.

Example, R64: IF the parse fails or times out (20 s), THEN THE SYSTEM SHALL show "Couldn't read that — try again", a Try again button that resends the same text, and a smaller "or fill in the form". Likely follow-upHow does that map to a test?

Architecture and request routing 8

Q23★Walk me through exactly what happens when I add an expense.

SayThe form calls the Server Action createExpenseAction with the token, the input and my member id from localStorage. On the server, createExpense resolves the group from the token and loads its members. prepareExpense validates with zod, checks every member id belongs to the group, gets the exchange rate (identity, cache, Frankfurter or manual), and buildExpenseAmounts computes the splits, payers and base-currency amounts while asserting the invariants. Then one RPC, create_expense, writes everything in a single Postgres transaction: it re-checks membership, re-checks Σpayers = Σsplits = total in both currencies, and logs activity. Finally refresh() re-renders the page, and readGroup recomputes balances and the plan.

Likely follow-upWhy check the invariants twice?

Defence in depth. TypeScript catches logic errors with a clear message; the SQL check guarantees nothing inconsistent can ever be stored, even if some future caller skips the TypeScript.

Q24Why Server Actions for some things and Route Handlers for others?

SayServer Actions suit form-style mutations: typed calls, no hand-written endpoints, and refresh() to re-render. Route Handlers suit things that need real HTTP: multipart image upload, the long AI calls with status codes (413, 415, 429, 502), CSV download, and the public /api/health for the keep-alive.

Likely follow-upHow long can those handlers run?

The receipt extract route sets maxDuration = 60 with a 25 s Gemini timeout, and the parse route has a 20 s deadline. Vercel's 4.5 MB body limit is well above the 1 MB upload cap.

Q25Where does business logic live, and why there?

SayIn lib/*: pure TypeScript with no React, Next, Supabase or fetch imports, and I/O injected where needed (for example the rate fetcher). That makes it unit-testable, including property tests and brute-force checks. server/* is the glue (validation, group from token, ownership checks, RPC calls), and the database enforces the final invariants.

Likely follow-upGive an example of injected I/O.

getRate in lib/currency.ts takes RateDeps: cacheGet, cacheSet, fetchJson and today. The tests pass fakes for timeouts and cache misses; production passes the fx_rates table and fetch. The parse route does the same with createParseHandler(deps).

Q26How is the group found for each request?

SayFrom the URL token. findGroupByToken first checks the format (22–64 base64url characters); a malformed token returns null and the page shows the same 404 as an unknown token (R1, AC-26). The group layout resolves the token before streaming, so unknown links get a real HTTP 404.

Likely follow-upWhy the same 404 for malformed and unknown tokens?

So responses don't reveal anything. Both look identical: "Group not found".

Q27How do pages get fresh data after a change?

SayEach Server Action ends with refresh() from next/cache (unless told not to), which re-renders the Server Components. Group pages call readGroup, which recomputes balances from the database. There's no client-side cache that can drift from the database.

Likely follow-upWhat about other people's changes?

They appear when you refresh or navigate. Real-time updates are a non-goal.

Q28How do recurring expenses get created without a cron job?

SayLazily. readGroup calls materializeRecurring before computing anything. It creates every occurrence that's due, dated on its own occurrence date, via the generate_recurring RPC. The expenses table has a unique (recurring_rule_id, recurring_occurrence) constraint, so the same occurrence can't be stored twice.

Likely follow-upIsn't it odd that an expense appears only when someone opens the group?

Each one is dated on its occurrence date, so balances are correct the moment anyone looks (risk K13, accepted). It avoids a scheduler and Vercel Cron, which was a non-goal.

Q29Where is per-device state kept, and why not on the server?

SayIn localStorage: which member you are per group (quits:me:{token}), your theme (quits:theme), and "Your groups" (quits:recent). None of it needs to be shared, and there are no accounts to attach it to. Every access is wrapped in try/catch, so blocked storage just means an empty list or the default theme.

Likely follow-upDoes the server ever see the 'Your groups' list?

No. The links even use prefetch={false}, so loading the home page requests none of the listed groups. A headless check showed 12 requests, none containing a token.

Q30How do the Gemini calls stay off the client?

SayThe browser posts to Route Handlers on our own domain. Only server/gemini.ts holds GEMINI_API_KEY (import "server-only"). AC-42's production network log showed 0 requests to generativelanguage.googleapis.com and 0 to supabase.co.

Likely follow-upWhy does that matter?

A key in the browser can be stolen and used to drain the quota or bill me. On the server it's protected, and the server enforces size checks and daily limits before any model call.

Backend and APIs 7

Q39List the HTTP endpoints you have.

Say/api/g/[token]/receipts/extract (POST multipart: receipt image to a draft), /api/g/[token]/expenses/parse (POST JSON: type-to-add prefill), /api/g/[token]/export.csv (GET: CSV download), and /api/health (GET: {"ok":true} or 503). Everything else goes through Server Actions in app/actions.ts.

Likely follow-upWhich status codes does the extract route return?

404 for an unknown group, 413 for over 1 MB, 415 for a type that's not JPEG, PNG or WebP by magic bytes, 429 for daily limits, 502 for "Couldn't read this receipt" with a reason, and 200 with the receiptId.

Q40How do you validate input?

SayWith zod on every server entry point: expense input, group settings, receipt drafts, the parse request body, and every model output. Then domain validation in lib (split sums, payers summing to the total, UPI ID format), then database checks and constraints. Errors become AppError with a code and field messages, which the UI shows next to the field.

Likely follow-upWhy validate Gemini's output if you gave it a JSON schema?

The schema shapes the output but doesn't guarantee valid values: amounts can be negative or strings can be wrong. zod plus deterministic checks are the real contract, and anything invalid becomes blank and flagged, never guessed.

Q41How do errors flow from the database to the user?

SayRPC functions raise named exceptions like NOT_FOUND, BASE_CURRENCY_LOCKED or INVARIANT_VIOLATION. rpc() maps them through fromDbError to an AppError with an HTTP-like status and a friendly message. The Server Action's run() turns AppError into {ok:false, message, fields}. Unknown errors log only the error name and return "Something went wrong. Please try again."

Likely follow-upWhy log only the error name?

To avoid leaking secrets or user data into logs (R51). Logs show which kind of failure happened, not the payload.

Q42How do the daily rate limits work?

SayA rate_limits table keyed by bucket and day. bump_rate_limit increments a bucket and returns the new count. Receipt scans bump scan:group:{id} (limit 30) and scan:app (300); type-to-add bumps its own group bucket (50) plus the shared app bucket. Both run before any Gemini call. Limits are configurable by env var, and days are IST dates.

Likely follow-upIs that race-free?

Yes. bump_rate_limit is a single statement: insert … on conflict (bucket, window_start) do update set count = count + 1 returning count. Postgres makes that upsert atomic, so concurrent requests each get their own count back and compare it with the limit.

Q43How is the exchange rate fetched and cached?

SayresolveRate: if the expense currency equals the base currency, the rate is identity. A valid manual rate wins if given. Otherwise check the fx_rates cache for that date, then call Frankfurter v2 /v2/rate/{BASE}/{QUOTE}?date= with a 5 s timeout and parse it with zod. Future dates request the latest rate and aren't cached. On failure with nothing cached it returns RATE_UNAVAILABLE, and the UI asks for a manual rate.

Likely follow-upWhat did you learn about Frankfurter in Phase 1?

The probe confirmed the v2 endpoint and response shape: weekends return a blended rate for that date, future dates return 404, and unknown currencies return 422. That became SC-1 in SPEC v0.4.

Q44How does the CSV export work?

SayA GET route, /api/g/[token]/export.csv, resolves the group and builds the file with the hand-written lib/csv.ts (buildCsv). It has a UTF-8 BOM so Excel shows ₹ correctly, RFC 4180 quoting, one row per expense and settlement in date order, and an "owes:{name}" column per member. It downloads as quits-{group-slug}-{date}.csv (R43). No library is used, following the PLAN's dependency rule.

Likely follow-upWhat about CSV injection?

Handled. guardCell prefixes a ' to any cell that starts with =, +, -, @, tab or CR, so a description like =HYPERLINK(...) can't run as a formula in Excel. Then quoteCell applies RFC 4180 quoting.

Q45How do you keep the share and reminder messages correct?

Saylib/share.ts builds them as exact strings that are unit-tested. INR groups use "₹" with Indian digit grouping (₹1,20,000); other currencies use their own format (D-26). waLink URI-encodes the text, so "₹" becomes %E2%82%B9 (AC-54). Share uses the Web Share API first, then wa.me; Copy is always available on desktop.

Likely follow-upDo you store phone numbers for reminders?

No. Remind opens WhatsApp with the message prefilled, and the user picks the contact there (R69).

Database and data model 8

Q46Describe your data model.

Saygroups (share_token, name, base_currency, is_demo); members per group with display order, optional UPI ID and archived_at; expenses with currency, the stored FX rate, rate date, source and the base amount; expense_payers and expense_splits as (expense, member) rows in both currencies; settlements; receipts with items and assignees; recurring_rules; activity; fx_rates; rate_limits; and _health. Likely follow-upWhy store payers and splits as separate rows?

So that "how much did each person pay and owe" is plain data, constraints can enforce non-negative amounts, and SQL can re-check Σpayers = Σsplits = total for every expense.

Q47Why store the exchange rate on each expense?

SaySo balances never change when rates move later, and anyone can see the rate and its date (R15–R17). Editing only the description keeps the rate; changing the date re-fetches it (AC-8). The base currency itself is locked after the first expense (D-1).

Likely follow-upWhy lock the base currency?

Changing it would require reconverting every expense at some rate, which changes history. BASE_CURRENCY_LOCKED is raised in SQL.

Q48Why soft delete?

SayAnyone with the link can delete (D-11), so mistakes and mischief must be reversible. Expenses and settlements get deleted_at and are excluded from balances. Activity logs the deletion, and Restore brings them back (R11, R12).

Likely follow-upAre deleted rows ever purged?

Not in this version, except that whole demo groups are deleted after 7 days.

Q49Tell me about the foreign-key problem you hit.

SayMember foreign keys on payers, splits and settlements were RESTRICT, which is checked immediately. Deleting a whole group (demo reset, test cleanup) failed even though the same statement would cascade those rows away. NO ACTION (migration 000300) still fired mid-cascade. DEFERRABLE INITIALLY DEFERRED (000400) checks at commit, after the cascade, while deleting a still-referenced member on its own still fails.

Likely follow-upWhy not just ON DELETE CASCADE from members?

Then deleting one member would silently delete expense rows and break other people's balances. Members are archived, not deleted; only whole-group deletion should cascade.

Q50Why are writes done in Postgres functions?

SayOne RPC call is one transaction, so an expense, its payer and split rows, the invariant check and the activity entry are all-or-nothing. The functions also re-check that every member id belongs to the group, and only service_role can execute them.

Likely follow-upIsn't business logic in SQL hard to test?

The money logic stays in lib, which is unit-tested; SQL only stores and re-checks. The DB integration tests (24) exercise the RPCs against the real database, including cross-group attacks.

Q51What constraints protect data quality?

SayChecks: the share_token format, name lengths, base_currency like ^[A-Z]{3}$, amount_minor > 0, non-negative payer and split amounts, the category list, fx_source in (identity, frankfurter, manual), a UPI ID format check, from ≠ to on settlements, and the activity action list. Unique keys: the token, a case-insensitive member name per group, display_order per group, and (recurring rule, occurrence).

Likely follow-upWhat broke in the UPI check?

Q52Which indexes exist, and why?

Sayexpenses (group_id, expense_date desc, created_at desc) for the newest-first list; settlements (group_id, settled_on desc); activity (group_id, created_at desc); receipts and recurring_rules by group; and a partial index on demo groups' created_at for the 7-day cleanup.

Likely follow-upAny query that doesn't scale?

readGroup loads all of a group's expenses to compute balances. That's fine for student groups, but a large group would want cached or materialized balances.

Q53How is the activity log structured?

Sayactivity rows hold the group, the actor (optional, the device's chosen member), an action from a fixed list (expense.created, settlement.deleted, demo.reset…), the entity type and id, a human summary like "Amount ₹500.00 → ₹600.00", and details as jsonb. Each RPC writes it in the same transaction as the change.

Likely follow-upCan the actor be faked?

It's the self-declared member. The server checks it belongs to the group, but it's not authentication.

Algorithms: minimum payments 12

Q54★Explain how Quits finds the minimum number of payments.

SayFirst compute each member's balance and drop the zeros, leaving n people who owe or are owed. If you can split those n people into k separate groups that each sum to zero, every group can settle internally with (size − 1) payments, giving n − k in total. So the minimum is n − k with k as large as possible. I find the largest k with a dynamic program over all subsets (a bitmask DP), then run greedy inside each group to produce the actual payments.

Likely follow-upWhy is the answer exactly n − k and not just at most?

It's a matching lower bound. Draw payments as edges: every connected component must net to zero, so the components are zero-sum groups and there are at most k of them. A component of m people needs at least m − 1 edges, so any plan has at least n − k payments.

Q55★Show me an example where greedy is not optimal.

SayAC-9, the same shape as the demo: A +400, B +300, C +300, D −600, E −400. Greedy (biggest debtor pays biggest creditor) gives D→A 400, E→B 300, D→C 200, E→C 100: 4 payments. But {A, E} sums to zero and {B, C, D} sums to zero, so k = 2 and the optimum is 5 − 2 = 3: E→A 400, D→B 300, D→C 300. In the demo, Settle says "3 payments instead of 10", and How? shows Greedy 4 and Optimal 3.

Likely follow-upWhere does 10 come from?

That's the naive count: pairs of members with a nonzero pairwise debt if nobody simplifies. In the demo, all 10 pairs among the five members have a nonzero net.

Q56Write the DP recurrence.

SayFor each subset mask: sums[mask] = sums[mask minus its lowest member] + that member's balance; dp[mask] = max over members j in mask of dp[mask minus j], plus 1 if sums[mask] is 0. The answer is k = dp[full set]. Intuitively, add people one at a time; each time the running total returns to zero, a zero-sum group has closed, and the DP picks the order that closes the most groups.

Likely follow-upWhat's the complexity?

O(n · 2ⁿ) time and O(2ⁿ) memory. At n = 18 that's 262,144 states × 18 ≈ 4.7 million steps, stored in a Float64Array and an Int32Array.

Q57How do you turn k into actual payments, deterministically?

SayRecovery: start from the full set and repeatedly remove the lowest-index member that keeps dp optimal. Whenever the remaining set sums to zero, one group ends. Groups are sorted by their earliest member, and greedy runs inside each group in member order, with ties broken by display_order. So the same balances always give the same plan; AC-12 checks two runs are deep-equal.

Likely follow-upWhy does determinism matter?

Two people looking at Settle on different phones must see the same suggested payments, or they'd pay the wrong person.

Q58Why do you cap the exact algorithm at 18 people?

SayThe DP is exponential. 2¹⁸ states are milliseconds, and AC-12 requires 18 random balances to solve in under 2 s. At 19 or more nonzero balances the plan falls back to greedy, the algorithm is reported as "greedy" with the optimal count null, and How? says "not computed (> 18 people)". Groups are capped at 50 members, but more than 18 nonzero balances is rare for students.

Likely follow-upCould you push the cap higher?

Each extra person doubles the work and memory. Something like 22–24 might be feasible with typed arrays, but beyond that you'd want a different method, such as an ILP solver or heuristics, and you'd lose the simple proof.

Q59Is minimizing the number of payments an easy problem?

SayNo, it's NP-hard in general. Maximizing the number of zero-sum groups contains Subset-Sum and Partition: even deciding whether the balances can be split into two zero-sum halves is the Partition problem. That's why an exact answer needs exponential time, and why I bound n.

Likely follow-upThen why bother with exact?

For realistic groups it's instant and provably minimal, which is a real product edge: fewer UPI payments to make. Greedy remains the fallback.

Q60How do you know your DP is correct?

SayThree ways. AC-11 compares it with a brute force over all set partitions on 300 random cases with n ≤ 8; they must agree, and the optimum must be ≤ greedy. AC-9 checks exact payment lists, and applyPayments must zero every balance. Edge cases: all zeros give 0 payments, and {+x, −x} gives 1.

Likely follow-upWhat's the brute force?

It enumerates every way to partition the people into groups, keeps the partitions where every group sums to zero, and takes the one with the most groups. Exponential, but fine for n ≤ 8.

Q61Define the naive count precisely. Why show it?

SayNaive (R21, D-8): for each expense, each participant owes each payer in proportion to what that payer paid, allocated with the largest-remainder rule. Settlements reduce the pair. Then count the pairs of members whose net is nonzero. It represents "everyone pays back whoever paid for them" with no netting, so "3 instead of 10" shows the user what simplification saved.

Likely follow-upGive the AC-10 example.

A pays ₹300 and B pays ₹600, each split equally among A, B, C. The pairwise nets are A owes B ₹100, C owes A ₹100 and C owes B ₹200, so naive = 3. Balances are A 0, B +300, C −300, so greedy = optimal = 1: C→B ₹300.

Q62How does greedy break ties, and why does it matter?

SayGreedy picks the most negative debtor and the most positive creditor; ties go to the earlier member in display order. In AC-9, B and C tie at +300 in step 2 and B wins. It matters for determinism: the exact sequence is part of the spec, so the tests can check it.

Likely follow-upIs greedy bounded?

Yes. Each step zeroes at least one person, so it uses at most n − 1 payments. The DP can only improve on that by finding more than one zero-sum group.

Q63Why use a Float64Array for the subset sums? Isn't floating point risky?

SayThe values are integer paise, and doubles represent integers exactly up to 2⁵³ (about 9 × 10¹⁵). Balances are bounded far below that: amounts are capped at 10 million major units and groups at 50 members. So every sum is exact and the "== 0" test is safe. Typed arrays keep the 2ⁿ table compact and fast.

Likely follow-upWhat would you do if amounts could be larger?

Use BigInt64Array or check magnitudes first. money.ts already uses BigInt for products in allocation, for the same reason.

Q64Does the minimum-payment plan ever make someone pay a stranger?

SayIt can make someone pay a different person than the one who actually paid for them, because it nets debts across the group. That's inherent to simplification. In student groups everyone knows each other, and each payment is shown clearly as "Kabir pays you ₹4,000.00" with a QR.

Likely follow-upCould you offer an alternative view?

Yes. A future option could show the pairwise (naive) payments for people who prefer paying back directly, at the cost of more payments.

Q65What happens to members with a zero balance?

SayThey're filtered out before planning (settle() keeps only nonzero balances), so they never appear in payments, and n counts only people who owe or are owed. If everyone is at zero there's no headline, and Settle shows "Everyone is settled up".

Likely follow-upAnd the headline when nothing simplifies?

paymentHeadline returns "2 payments" with no "Simplified" badge when the listed count equals naive, and null when there's nothing to pay (AC-57).

Money: integer paise, largest remainder, currencies 8

Q66★How do you guarantee every group's balances sum to exactly zero?

SayThree layers. All amounts are integer paise: no floats, and products are computed in BigInt. Every split is allocated with the largest-remainder rule, so the shares always add up to the total exactly. And the invariants are checked: buildExpenseAmounts asserts Σpayers = Σsplits = total in both currencies, the SQL function re-checks it, and readGroup refuses to show a group if Σbalances ≠ 0. AC-5 is a property test over 1,000 random groups.

Likely follow-upWhy not just use decimals?

Decimal libraries add a dependency and still need a rounding policy for splitting. Integers plus an explicit allocation rule make the rounding visible, deterministic and testable.

Q67Explain the largest-remainder rule with an example.

SayGive everyone the rounded-down share, then hand out the leftover paise one at a time to whoever has the biggest fractional remainder, with ties going to the earlier member. ₹100.00 among three people: each gets 3333, and 1 paisa is left; the remainders are equal, so the first member gets it, giving [3334, 3333, 3333]. 999 paise by 50/25/25%: the floors are 499, 249, 249, the remainders .5, .75, .75, so the two 25% people get +1, giving [499, 250, 250].

Likely follow-upIsn't giving the extra paisa to the first member unfair?

It's at most one paisa per expense. The rule is deterministic and documented (R13), and it uses display order, which everyone can see. Making it random would make the app non-reproducible.

Q68Why BigInt in allocate()?

SayThe intermediate product total × weight can be large. Percentages are basis points (100.00% = 10000), and shares and amounts can be big. BigInt makes overflow impossible, so floor and modulo are exact. Results are converted back to Number only once they're known to be safe integers.

Likely follow-upHow are percentages stored?

As basis points: 33.33% is 3333. percentToBasisPoints accepts up to 2 decimals, and the percentages must sum to exactly 10000.

Q69How do you convert a foreign-currency expense?

SayConvert the total once: base = round_half_up(amount × rate × 10^(exp_base − exp_src)), using exact decimal maths with BigInt. Then allocate that base total across payers and splits by their exact original proportions with the largest-remainder rule (R17, SC-3). AC-6: USD 12.34 at 83.4567 is 102986 paise, and an equal split of 3 gives [34329, 34329, 34328]; JPY, with exponent 0, works the same way.

Likely follow-upWhat rounding is used, and why half-up?

Half away from zero (divRoundHalfUp). It's the familiar commercial rule. AC-6's THB case checks it: 2361.75 becomes 2362.

Q70What about a discount bigger than the tax on a receipt?

SayThen the remainder (printed total − Σitems) is negative. allocate() handles negatives by allocating |total| and negating, so everyone's share of the discount is proportional and the owed amounts still sum exactly to the printed total. AC-18 tests this.

Likely follow-upCan someone's owed amount go negative?

The test asserts all owed values stay ≥ 0 in that case. A remainder can't exceed the item subtotal unless the receipt is very odd, and the mismatch banner would show first.

Q71How do you display money without rounding errors?

SayformatMoney turns minor units into an exact decimal string first (minorToMajorString), then passes that string to Intl.NumberFormat("en-IN"), which accepts decimal strings. So ₹1,23,456.78 is formatted without ever being a float.

Likely follow-upWhy en-IN?

Indian digit grouping (lakhs and crores) is what the users expect. Share messages use "₹" with Indian grouping for INR groups (D-22), and each currency's own format otherwise (D-26).

Q72How do you parse what users type, like '1,240.50'?

SayparseMajorInput strips spaces, commas and ₹, accepts an optional minus and decimals, and rejects more decimal places than the currency allows (for example 3 decimals for INR). It then converts exactly to minor units with decimalToMinor, which uses BigInt decimal parsing rather than float multiplication.

Likely follow-upWhy not parseFloat × 100?

Floats can't represent many decimals exactly, so 1.005 × 100 doesn't come out as you'd hope. Parsing the digits as a string avoids that.

Q73What's the balance formula?

Saybalance = Σ paid (base) − Σ owed (base) + Σ settlements sent − Σ settlements received. Positive means the group owes you ("gets back ₹X"); negative means you owe ("owes ₹X"). Deleted expenses and settlements are skipped. AC-4: A pays ₹300 split among A, B, C gives A +200, B −100, C −100.

Likely follow-upWhy does sending a settlement increase your balance?

Paying someone reduces your debt. If you were at −100 and pay 100, you go to 0, and the receiver's positive balance drops by the same amount, so the sum stays 0.

Gemini receipt pipeline 8

Q74★How does receipt scanning work end to end?

SayThe phone compresses the photo in the browser to under 1 MB and uploads it to the extract route. The route checks the size (413), the file type by magic bytes (415) and the daily limits (429) before any AI call. Then Gemini reads it with a fixed prompt and a JSON schema, at temperature 0, within 25 s. zod validates the result and converts it to paise, and it's saved as a draft; the image is never stored. In the review screen you can edit everything, a mismatch banner appears if the numbers are off by more than ₹1, and each person taps what they had. Finalizing makes one expense for the printed total, with tax and service shared in proportion to what people ate.

Likely follow-upWhat exactly is the 'mismatch'?

diff = total − (Σitems + tax + service + tip − discount + round_off). If |diff| is over ₹1 (100 paise), the banner shows and the expense gets a mismatch badge (R33, R35).

Q75Why compress in the browser?

SayPhone photos are often 3–10 MB. Compressing to at most 1 MB on the device makes uploads fast on mobile data and keeps well under Vercel's body limit (risk K4). It also sends less personal data to Google. compress.ts redraws the image on a canvas (longest edge ≤ 2000 px, JPEG quality 0.85 down to 0.5, then smaller), applies the EXIF orientation, and fills transparency with white.

Likely follow-upAnd if it's still too big?

It keeps shrinking the image down to a 500 px edge. If it still doesn't fit, it shows "This image is too large to upload, even after compression." The server also rejects anything over 1,048,576 bytes regardless.

Q76Why share tax and service in proportion instead of equally?

SayFairness. If I had a ₹480 prawn curry and you had a ₹180 dessert, I should pay more of the GST and service charge. The remainder (printed total − Σitems) is allocated by each person's item subtotal with the largest-remainder rule. AC-18: subtotals 30000/20000/30000 and a printed total of ₹845 give a remainder of 4500 allocated [1688, 1125, 1687].

Likely follow-upWhy use the printed total instead of the computed one?

D-3: the printed total is what was actually paid. Any unexplained difference is shared rather than lost, and the mismatch badge tells people to check.

Q77What if Gemini reads the receipt wrong?

SayNothing is final until a human reviews it. Every field is editable, items can be added or removed, and the mismatch banner catches inconsistent totals. If Gemini fails outright (timeout, error, invalid output), the user gets "Couldn't read this receipt" with Retry or "Enter items manually". The eval measures how often it's right.

Likely follow-upHow often is it right?

Small sample, n = 5. In the main run 3, every answered receipt was read perfectly (F1 1.00, totals right, all reconciled), but one of five timed out at 25 s. Across runs, totals were right on every receipt that was answered.

Q78What did the D-34 prompt fixes change, and how were they found?

SayRun 2 saved its predictions (D-32), which explained two misses. r01: an add-on line under an item ("Dimsums Extra … = 150") was read as a separate item, so ₹150 was counted twice. r04: a delivery app's ₹14.99 platform fee was dropped. Both would affect real splits, so they were fixed as product bugs: add-on lines belong inside their item, and platform, packaging, convenience and delivery fees go in service_charge. Unit tests pin the rules, and run 3 is labelled not blind for those two receipts.

Likely follow-upDid the fixes work?

r04 reconciled in run 3, with the fee read as service. r01 timed out in run 3, so the add-on fix wasn't measured on a real receipt; I say that openly.

Q79Why don't you store the receipt image?

SayD-2: it's personal data we don't need after extraction, and storing it would cost space and create privacy risk. Only the extracted and edited values are kept. The scan screen says so: "The photo is sent to Google Gemini to read it and is not stored by Quits."

Likely follow-upWhat if a user wants to see the original later?

They'd keep the photo themselves. Storing images, for example in Supabase Storage, is an explicit non-goal.

Q80How do you stop someone abusing the scan endpoint to burn your Gemini quota?

SaySeveral guards run before the model call: the group must exist, the body must be at most 1 MB, the magic bytes must be JPEG, PNG or WebP, and daily counters allow 30 scans per group and 300 AI calls per app. The app-wide bucket is shared with type-to-add. Both limits are env vars.

Likely follow-upCould someone just create many groups?

Yes, which is why there's an app-wide cap too. Per-IP limits or a CAPTCHA would be next if abuse appeared.

Q81Why structured output with a JSON schema instead of asking for JSON in the prompt?

SayresponseJsonSchema makes the model's output follow the shape (fields, types, required keys), so parsing rarely fails. I still validate with zod and convert units myself. SC-2 recorded that responseJsonSchema is the field in @google/genai 2.x that takes a plain JSON Schema.

Likely follow-upWhy temperature 0?

It's an extraction task, not a creative one. Temperature 0 gives the most consistent reading for the same image.

Type-to-add pipeline 8

Q82How does type-to-add work?

SayYou type or dictate a sentence like "Rohan paid 600 for pizza, split with Kabir and me". The parse route checks the limits and sends Gemini the sentence plus context: the members' first names, the base currency, and today with its weekday. Gemini returns structured JSON. Then deterministic code (resolveNl) matches names, maps "me" and "everyone", validates every field, and leaves anything unclear blank and flagged. The form fills in, and nothing is saved until you tap Save.

Likely follow-upWhat does 'flagged' look like?

The field is left blank and highlighted with a reason, such as "Couldn't find 'Karan'" for an unknown name, an ambiguous name, an invalid value, or a person listed twice in the split.

Q83Why not let Gemini match names to members?

SayName matching must be exact and explainable. Code matches the full or first name case-insensitively: one match is used, no match is "unknown", two matches are "ambiguous". It never creates a member. The words for "me" (me, I, main, maine, mujhe, mera) and for "everyone" (everyone, all, sab, sabhi, sab log, hum sab…) are matched in code too (D-23, D-24), so Hinglish works reliably.

Likely follow-upWhy send Gemini first names only?

People usually say first names, and it gives the model less to confuse. Full-name disambiguation happens in code.

Q84What happens with two members called Rahul?

Say"Rahul" matches two first names, so matchName returns "ambiguous". The field is left blank and flagged instead of guessing. Ambiguous cases like this are part of the eval's correct-abstention metric.

Likely follow-upAnd 'Rahul Singh'?

A full-name match wins if it's unique, so "Rahul Singh" resolves correctly.

Q85Why doesn't type-to-add save automatically?

SayR64: models misread intent, so the safe design is "fill the form, the human confirms". The route has no save dependency at all; the unit test even checks there's no createExpense in its dependencies. The only database write is the rate-limit counter.

Likely follow-upIsn't that slower for users?

One extra tap, but it catches a wrong payer or amount before it hits everyone's balances. Undoing a wrong expense later is worse.

Q86What did you find when you investigated the type-to-add failures?

SayI classified every failure from runs 1–2 and ran a 60-call probe. Every error was HTTP 503 "high demand", with no 429s, and some errors arrived after 12 s. No answered call took longer than 12.4 s. Thinking wasn't the cause: 0 thinking tokens either way, and thinkingBudget: 0 is rejected. Conclusion: with a 15 s limit, the retry had no time left, so it was a timing and UX problem, not a prompt problem.

Likely follow-upSo what changed?

SPEC v1.0: the limit went from 15 s to 20 s, with a wait of about 1 s before the single retry (D-29). There's a Try again button and "Still reading… Gemini is busy" after about 6 s (D-28), and real HTTP statuses are recorded (D-30).

Q87Why only one retry, and why wait 1 s?

SayMore retries would blow the 20 s deadline and multiply load while Gemini is already overloaded. Retrying instantly after a 503 usually hits the same overload, so a short pause gives it a chance. The user can always tap Try again.

Likely follow-upWhy not exponential backoff?

Within a 20 s budget for a single interactive request, one delayed retry is about all that fits. Backoff makes sense for background jobs.

Q88Why didn't you add a fallback model?

SayThat was proposal Q4, and I rejected it. A second model would need its own prompt testing and its own eval, and it would make results harder to interpret. The failures were capacity (503) and timing, which the UX change and timeout handle. It's recorded in D-30.

Likely follow-upWould you add it in production?

Possibly, with paid quota, and only after evaluating it on the same 30 sentences and reporting it separately.

Q89How does it handle 'split with Amit and me' versus a treat?

SayD-21: "X paid 600, split with Amit and me" includes X unless the text excludes them ("only for Amit and me"). An explicit list of shares or amounts per person is the complete split, so the payer isn't added. A "treat" means the payer covers it all and is the only participant. The prompt and the eval ground truth both follow this.

Likely follow-upWhere did that rule come from?

It was open question OQ-18, decided as D-21 and clarified in v0.9 while reviewing the eval sentences, before the first eval run.

Evaluations and metrics 12

Q90★How did you measure accuracy, and what were the results?

SayThere are two evals, both run through the app's own pipeline and published on /about. Receipts: 5 real bills (n = 5, small sample). The main run 3 answered 4 of 5; those 4 were perfect (F1 1.00, totals right, all reconciled), but overall F1 is 0.452 because the fifth timed out. Type-to-add: 30 sentences, 7 deliberately ambiguous. Run 3 answered 24 of 30 within 20 s, with amount and exact match 95.8% on those; overall both are 76.7%. I report answer rate and accuracy-when-answered separately, because "Gemini was busy" isn't the same as "wrong".

Likely follow-upSo did you meet your targets?

No. Both Should-level targets fail on the overall numbers: AC-25 (receipt F1 ≥ 0.80) and AC-52 (amount ≥ 95%, exact ≥ 80%). Accuracy-when-answered meets them, but I report the overall figures as the result.

Q91How did you create the receipt ground truth?

SayI took 5 real receipts (3 restaurant bills, 2 delivery screenshots) and covered personal details. Claude drafted each ground-truth JSON by reading the images, without using Gemini or the extract route, because the model under test can't grade itself. I then checked every value against the paper bills, settled a few labelling rules, and marked each file reviewed.

Likely follow-upWhat labelling rules?

An add-on stays inside its item's amount, a voluntary staff contribution and platform fees count as service charge, and a delivery app's total is the amount actually paid after coupons (r04: 87.69, not 227.69).

Q92Explain your item matching and precision/recall.

SayA predicted item matches a true item if the amounts are within ₹1 and the names are at least 60% similar (1 − Levenshtein distance ÷ the longer length, after normalizing case and punctuation). Matching is one-to-one, highest similarity first. Precision = matched ÷ predicted, recall = matched ÷ true, F1 is their harmonic mean, all micro-averaged over every item. AC-23 checks it: 4 true, 3 predicted, 2 matched gives P 0.667, R 0.5, F1 0.571.

Likely follow-upWhy micro-average?

Receipts have very different item counts (34 versus 2), and micro-averaging weights every item equally. The per-receipt table is also published.

Q93What's 'answer rate' versus 'accuracy when answered', and why split them?

SayAnswer rate is the share of inputs that got a usable answer within the time limit. Accuracy when answered is measured only on those. Overall accuracy treats a timeout or a 503 as wrong on every field, which mixes infrastructure problems with model quality. D-31 and D-35 require both figures for every run, computed from the saved results with no re-runs.

Likely follow-upIsn't that a way to hide bad numbers?

No. The overall numbers are still the headline, and both targets are judged on them. The split just shows where the problem is: reliability, not reading accuracy.

Q94What does 'blind' mean, and which of your runs aren't?

SayA run is blind if nothing was changed after seeing that eval's results. Type-to-add run 2 isn't blind for P3 (duplicate names leave the split blank), and run 3 isn't blind for P3 or the 20 s timeout. One clarifying prompt line was even added before run 1, while reviewing the ground truth. Receipt run 3 isn't blind for r01 and r04, after the D-34 prompt fixes. Every report says this.

Likely follow-upHow would you get a truly blind number?

Hold out a fresh test set that's never looked at during development, freeze the prompt, and run it once. That's on my future list.

Q95Why did receipt run 3's recall drop to 29.2%?

Sayr01 is a 34-item bill, and it didn't get an answer within 25 s in run 3. Its 34 items count as missed, out of 48 true items in total, so recall is 14/48 = 29.2%. The 4 receipts that were answered were read perfectly. That's exactly why answer rate is reported separately.

Likely follow-upWhy not raise the receipt timeout?

Possibly. The route allows 60 s and Gemini gets 25 s. But I didn't change it after seeing the result, to keep the evals honest, and long waits hurt the user experience. It's a reasonable next experiment, reported separately.

Q96How do you score type-to-add splits fairly?

SayD-27: two splits match if they give every participant the same amount in paise, using the same largest-remainder allocation in member order. So "shares 2:2:1:1:1 of ₹140" equals "exact ₹40/40/20/20/20". Split-type accuracy is still reported separately, and a blank (invalid) split matches only a blank split.

Likely follow-upWhy not just compare the split type?

The same split can be expressed several ways. Comparing the money each person owes is what users actually care about.

Q97What's 'correct abstention'?

Say7 of the 30 sentences are deliberately ambiguous, for example two members with the same name. For those, the right answer is to leave specific fields blank. Correct abstention is the share of those where every should-be-blank field was blank, so it measures whether the system guesses when it shouldn't.

Likely follow-upWhat was it?

71.4% in runs 1 and 2. In run 3 it was 57.1% overall, because only 5 of the 7 got an answer; on those 5 it was 4 of 5.

Q98Is n = 5 statistically meaningful?

SayNo, and the app says so: "n = 5, small sample", and one receipt moves a per-receipt rate by 20 points. Treat it as a sanity check and a regression harness, not a benchmark. With n = 30 for type-to-add, a single sentence is about 3.3 points. The value is in the honest method and the saved per-item predictions, not the headline number.

Likely follow-upHow many would you need?

To pin an accuracy near 95% within about ±5 points you'd want on the order of 70+ independent items, and more for per-category claims. The eval harness already supports that.

Q99Why keep every eval run instead of the best one?

SayOverwriting runs invites cherry-picking. Each run's results*.json and REPORT*.md are kept as they were, and each later report states what changed and whether it's blind. I also stopped re-running after run 3 (D-31, D-35), so the reported result isn't "the best of many attempts".

Likely follow-upWhich run is the 'main' result?

Run 3 for both evals: the latest code, honestly labelled. Earlier runs are shown under "Earlier runs" on /about.

Q100Who wrote the type-to-add sentences?

Say20 were drafted by Claude in English and Hinglish, about 5 of them deliberately ambiguous. 10 were written by me in my own words. I reviewed all 30 and corrected the ground truth: for example human-09 became "participants = Rahul only" and is no longer ambiguous. Each file fixes the members, who "me" is, and today's date, so the eval is deterministic apart from the model.

Likely follow-upIsn't it biased if the same AI wrote sentences and code?

Partly, which is why a third are mine, the ground truth was human-reviewed, and the known weak spot (human-06, with no payer named) is documented rather than tuned away.

Q101What's a known weakness you deliberately left in?

Sayhuman-06: "paid for the movie" with no payer named. The model may assume the speaker paid instead of leaving the payer blank. I didn't tune the prompt for it, because tuning on the eval set would make the eval meaningless. It's in the README's known limitations, with the advice to always check "Paid by".

Likely follow-upHow would you fix it properly?

Add more no-payer examples to a training or validation set, adjust the prompt, then measure on a fresh held-out set.

UPI and settle-up 6

Q102★Why does settle-up use a QR code instead of a 'Pay' button?

SayI tested it before building it. In Phase 1 (P1-8), on a Samsung phone against the deployed site, the upi://pay deep link was blocked by GPay, PhonePe and Paytm; GPay even showed a misleading "exceeded bank limit" error at ₹1. Scanning a QR shown on a laptop, or a QR screenshot from the gallery, worked with the payee and amount filled in. So SPEC v0.5 made settle-up QR-first. The deep link stayed as a best-effort extra labelled "May be blocked by some UPI apps".

Likely follow-upWhy do the apps block it?

I don't know their internal policy, and I didn't guess in the spec; I recorded the observed behaviour. Web-initiated P2P intents are a known fraud vector, which is a plausible reason, but the design only depends on what I measured.

Q103What's inside the UPI link and QR?

Sayupi://pay?pa={UPI ID}&pn={name}&am={rupees with 2 decimals}&cu=INR&tn={note}. pn and tn are URI-encoded, the @ in pa stays literal, and the note is "Quits: {group}", cut to 50 characters. AC-13 pins the exact string: upi://pay?pa=priya@okicici&pn=Priya%20S&am=450.50&cu=INR&tn=Quits%3A%20Goa%20Trip.

Likely follow-upHow is the UPI ID validated?

With the regex ^[a-zA-Z0-9._-]{2,256}@[a-zA-Z]{2,64}$ in code. Postgres can't use a {2,256} bound, so the database checks the same rule with char_length.

Q104How does Quits know a payment happened?

SayIt doesn't, by design. Quits never handles money. Scanning, saving or opening the QR records nothing. Only when someone taps "Mark as paid" and confirms is a settlement recorded, and balances update (R25). Someone can also record a cash payment manually.

Likely follow-upWhat if someone marks it paid without paying?

It's visible in the activity log and in Recent payments, and it can be deleted and restored. Trust within the group is assumed, as with the link model.

Q105How do the QR options help in practice?

SayThere are three ways because scanning your own phone's screen is impossible. "Save QR image" saves a PNG with the payee, amount and QR, which you open from the gallery in any UPI app. "Show full screen" lets a friend's phone scan it. On a laptop, the QR is just visible. "Copy UPI ID" with the amount in large text covers manual entry.

Likely follow-upHow did you check the saved image scans?

AC-14 on my phone: save, then scan from the gallery in a UPI app, with the payee and amount filled in. It was re-checked in the dark theme for AC-58.

Q106What's the 'set UPI ID from my QR' feature, and is it private?

SayR60: upload a screenshot of your own UPI QR, and it's decoded in the browser (the built-in BarcodeDetector, or jsQR otherwise). parseUpiUri extracts only pa (the ID) and pn (the name). Only those two values go to the server, never the image; the headless check saw a single 176-byte POST.

Likely follow-upWhy not just type the ID?

You can. Copying it from a QR avoids typos in IDs like 9876543210@ybl.

Q107Why are UPI actions only shown for INR groups?

SayUPI is a rupee system (D-4). A USD trip group shows the plan without QR codes. There's also a warning above ₹1,00,000, since UPI apps may cap a single payment (R26).

Likely follow-upWhat do non-INR groups use to settle?

"Mark as paid" or "Record a payment" with cash or other methods. The payment plan itself works for any currency.

Security and privacy 9

Q108★How is the data secured if there are no accounts?

SayThe browser never talks to the database. Supabase tables have RLS on with no policies, all privileges are revoked from the browser roles, and the database functions can only be executed by the service role. Only server code holds the secret key, in a module marked "server-only". Access to a group requires its 128-bit link token, and every server operation re-checks that the ids belong to that group, both in TypeScript and in SQL. I verified it: REST calls with the public key return permission denied on all 14 tables, and the production network log shows no requests to Supabase or Gemini from the browser.

Likely follow-upSo what's the weakest point?

The link itself. Whoever has it can edit. That's the stated trade-off, mitigated by noindex and no-referrer headers, soft delete and restore, and the activity log.

Q109Could someone guess or brute-force a group link?

SayThe token is 16 random bytes from a CSPRNG, which is 128 bits, encoded as 22 base64url characters. That's about 3.4 × 10³⁸ possibilities, so guessing is infeasible. Tokens also don't leak through Referer headers (no-referrer) and group pages are noindex, so search engines don't list them.

Likely follow-upWhat if a link leaks in a screenshot?

Then that group is exposed. Rotating links is a non-goal for now, and would be the fix (with deleting groups).

Q110What stops someone in group X from touching group Y's data?

SayEvery operation resolves the group from the token, then checks every member id it's given (payers, splits, actor, settlement parties) belongs to that group: assertMembersBelong in TypeScript and _assert_members in SQL. Expense and settlement lookups are scoped to the group. AC-43's DB tests try it: a member from another group returns 404 with no row created, and deleting Y's expense through X's token returns 404 with nothing changed.

Likely follow-upWhy check in both places?

Because the service role bypasses RLS, the app is the gatekeeper. Duplicating the check in SQL means a bug in one layer doesn't open the door.

Q111How did you make sure no secrets leaked?

SaySecrets live only in .env.local (gitignored) and Vercel env vars, and .env.example has names only. No NEXT_PUBLIC_* variable holds a secret. AC-42: grep found no key patterns in the built .next/static or in the full git history, and the production network log shows no calls to supabase.co or the Gemini API.

Likely follow-upHow did you stop the AI agent seeing keys?

.claude/settings.json denies reading .env.local, and the PLAN rule says never read or print it; scripts load it themselves with node --env-file. One gap: the agent once ran md5sum on the file to check it was unchanged. That reads the bytes, even though nothing was printed. A deny-list only blocks the commands it names, so next time I'd keep the secrets file out of the agent's workspace entirely.

Q112How do you protect the upload endpoint?

SaySize first: the Content-Length is checked, then the file must be ≤ 1,048,576 bytes (413). The type is checked by magic bytes, not by the file extension or Content-Type (415). Daily limits come before any model call (429). The image is only passed to Gemini and never stored or logged.

Likely follow-upWhy magic bytes?

Extensions and Content-Type headers are client-controlled. The first bytes of the file (FF D8 FF for JPEG, the PNG signature, RIFF…WEBP) tell you what it really is.

Q113What about XSS or injection?

SayReact escapes text by default. The only raw HTML is a constant theme script in the root layout. All SQL goes through parameterized RPC calls with typed arguments; there's no string-built SQL. CSV export guards against formula injection. Model outputs and request bodies are validated with zod.

Likely follow-upAnd prompt injection through a receipt or a sentence?

The model can only return JSON in a fixed schema, and code validates every field. It has no tools and can't write data. The worst case is a wrong prefill that the user sees and corrects before saving.

Q114What user data goes to third parties?

SayReceipt photos and type-to-add sentences go to Google Gemini. The scan screen says so, and notes that on the free tier Google may use inputs (risk K12). Exchange-rate requests to Frankfurter contain only currency codes and a date. Nothing else leaves: no phone numbers are stored, and "Your groups" stays on the device.

Likely follow-upWould you do anything differently for a real launch?

Use a paid Gemini tier with data-use terms that exclude training, add a privacy page, and offer a way to delete a group.

Q115Why the noindex and no-referrer headers?

SayGroup pages contain private data reachable by anyone with the URL. X-Robots-Tag: noindex, nofollow on /g/* keeps them out of search engines. Referrer-Policy: no-referrer means clicking an outbound link (like wa.me) doesn't send the group URL in the Referer header. AC-43 checked both with curl on production.

Likely follow-upAny other headers?

X-Content-Type-Options: nosniff on every route.

Q116Is the identity system secure?

SayIt's not authentication, and I don't claim it is. You pick your name on each device, it's stored in localStorage, and the server only checks that the chosen member belongs to the group. It exists for convenience ("You owe…", whose action it was), not access control.

Likely follow-upCould you add real identity cheaply?

An optional magic-link sign-in that maps an email to a member would work, while still allowing link-only use for people who don't sign in.

Testing, CI and quality 8

Q117★What's your testing strategy?

SayI test where bugs are expensive: money and correctness. There are 162 unit tests on the pure lib modules: exact-value ACs, a property test over 1,000 random groups, a brute-force comparison for the optimal algorithm, and mocked-Gemini tests for the AI routes. There are 24 DB integration tests against real Supabase for the RPCs, the RLS lockdown and cross-group attacks. CI runs lint, typecheck and unit tests on every push. UI checks were scripted headless-Chrome audits plus my own checks on production and an Android phone, recorded as evidence. Accuracy is measured by two evals.

Likely follow-upWhat's missing?

A committed end-to-end suite. The headless audits were scripts outside the repo, and turning them into Playwright tests in CI is the first thing I'd do next.

Q118Describe the property test.

SayAC-5: a seeded pseudo-random generator builds 1,000 random groups with 2–12 members and 1–40 expenses, using every split type, multiple payers, mixed currencies and settlements. For each group it asserts every expense's payers and splits sum to its total in both currencies, and that the balances sum to exactly 0. The seed makes failures reproducible.

Likely follow-upWhy both a property test and exact-value tests?

They catch different things. The property test proves sums always balance, but it can't tell a fair split from an unfair one that still sums correctly. Exact-value ACs pin the intended behaviour. For example, AC-6's expected [34329, 34329, 34328] is what showed that allocating by rounded cent shares (SC-3) would make an equal split unequal, even though the sums would still balance.

Q119Why aren't DB tests in CI?

SayThey need SUPABASE_DB_URL, the database password, and CI deliberately has no secrets: no GitHub secrets are configured at all. They run locally with npm run test:db, which skips cleanly without the URL. Test groups use a __test__ prefix, and there's a cleanup script.

Likely follow-upHow would you add them to CI?

Run a disposable Postgres in CI (for example a Supabase CLI or Docker service), apply the migrations, and run the same tests. That gives no shared secrets and isolated data.

Q120How do you test code that calls Gemini?

SayDependency injection. createParseHandler takes findGroup, loadMembers, bumpLimits, callModel and today as parameters, so the unit tests pass a fake callModel that returns JSON, hangs, or throws a 503. That checks the 20 s timeout, the delayed single retry, status reporting, the 429 and 400 paths, and that nothing is saved. extractReceipt takes a client function the same way.

Likely follow-upAnd real Gemini?

That's what the evals are for: the real model through the real pipeline, with the results saved.

Q121How did you test the UI without an E2E suite?

SayWith scripted headless Chrome over the DevTools protocol against a local production build and the real database. There were flows (create a group, add expenses, receipt paste, settle, identity) and audits at 360 and 1440 px in both themes: overflow, wrapped labels, 44 px tap targets, computed text contrast, truncation, the QR island, the "All groups" link and home order. The last audit was 104 runs, all clean. Then I did live checks on production and on my phone.

Likely follow-upWhy wasn't that committed?

Time. The scripts lived in a scratch folder and the evidence went into PLAN.md. That's the gap I'd close first, with Playwright.

Q122How did you stop tests being weakened to pass?

SayThe PLAN rule: never weaken, skip or delete a test to make it pass. If a requirement was wrong, stop and propose a spec change. The ACs have exact values from the spec, so a test can't quietly change its expectation without the SPEC changing too, and the SPEC changes are logged.

Likely follow-upDid a test ever have a wrong expected value?

Yes, in the polish work. The first expected "% of total" for seven equal categories was wrong: 1000 tenths ÷ 7 = 142 remainder 6, so six get 14.3 and one gets 14.2, not five and two. The expectation was corrected after checking the arithmetic; the code was right. The test now has that arithmetic in a comment.

Q123How do you test accessibility and theming?

Saytests/unit/theme.test.ts parses globals.css. It checks the dark and light token sets have the same names, that System in light mode equals Light, and that every text/background pair is at least 4.5:1 in both themes. It also checks the PWA theme colour equals the dark background, that the pre-paint script falls back to dark on blocked storage, that avatars meet AA, and that the QR is #000 on #fff with a 4-module margin.

Likely follow-upWhy parse CSS in a test?

So the tokens can't drift: someone changing a colour gets an immediate failing test if contrast drops below AA.

Q124What does CI run, and when?

Sayci.yml runs on every push and pull request, on ubuntu-24.04 with Node from .nvmrc (24): npm ci, lint, typecheck (next typegen plus tsc), and unit tests. Vercel builds separately on push to main. The keep-alive workflow is separate and only pings /api/health daily.

Likely follow-upDoes CI build the app?

Not in ci.yml; Vercel's build is the build check for main. Locally, the PLAN rules required npm run build before each commit from Phase 4 on.

Performance and scalability 5

Q125★What happens if 10,000 people start using Quits?

SayMost of it scales, because the per-request work is per group and groups are small. Vercel runs the Next.js functions on demand, and the database is accessed over Supabase's HTTP API rather than a long-lived connection per user. Three things would break first. (1) Gemini: the free tier and my app-wide daily cap of 300 AI calls would be used up within hours, so I'd need paid quota, and the cap would turn into a real cost control. (2) Supabase free: 500 MB and shared compute, which means upgrading the plan and watching the expense indexes. (3) readGroup recomputes balances from all of a group's expenses on every view, which is fine for 50 expenses but would want cached or materialized balances for very active groups.

Likely follow-upWhat about the minimum-payments algorithm under load?

It's per group and capped at 18 nonzero balances, so it costs milliseconds and doesn't grow with the number of users. It's CPU work inside one request, and nothing shared.

Q126How expensive is a group page load?

SayreadGroup loads the group and members, lazily creates any due recurring expenses, then loads all expenses and settlements. It computes the balances, checks they sum to zero, then computes the plan (DP up to 2¹⁸ states) and the naive count. Database work is a few indexed queries per group; CPU work is linear in the number of expenses plus the bounded DP.

Likely follow-upHow would you cut it down?

Keep a balances table updated in the same transaction as each write, and recompute the plan only when balances change.

Q127How fast are the AI features?

SayReceipts: the mean latency was 5.9 s in run 1 and 11.2 s in run 3, which includes a 25 s timeout. Type-to-add: in the 60-call probe no answered call took longer than 12.4 s, and the mean in eval run 3 was 9.4 s, also including timeouts, at a time when Gemini was under heavy load. The UI shows a skeleton and, after about 6 s, "Still reading… Gemini is busy".

Likely follow-upHow would you make them faster?

Paid quota with better availability, a smaller image for simple receipts, and for type-to-add a fast local path for very simple sentences ("Rohan paid 600"). That last one would need its own eval.

Q128How did you keep the frontend light?

SayMost pages are Server Components, so less JavaScript ships to the client. There's no UI component library; Tailwind and design tokens are used instead. Charts, CSV, Levenshtein and image compression are hand-written. The only runtime packages are next, react, react-dom, @supabase/supabase-js, @google/genai, zod, qrcode, jsqr and server-only.

Likely follow-upDid you measure the bundle size?

Not formally; I don't have a number to quote. A Lighthouse run and a bundle analysis would be the next step.

Q129Any concurrency issues at scale?

SayWrites are atomic database functions, so a half-written expense can't exist. Recurring generation is protected by a unique (rule, occurrence) constraint, so two people opening a group at once can't create the same rent twice. The rate-limit increment is an atomic upsert. The accepted gap is concurrent edits to the same expense: last write wins, with both edits in the activity log.

Likely follow-upHow would you add conflict detection?

An updated_at or version column checked in update_expense (optimistic concurrency), returning a "changed by someone else" error that the UI resolves.

Reliability and failure scenarios 6

Q130★What happens if the database or Gemini goes down?

SayDatabase down: pages fail with an error screen that has a retry button, Server Actions return "Something went wrong. Please try again." while keeping the user's input, and /api/health returns 503 {"ok":false}. Nothing is lost, because nothing was half-written. Gemini down: the receipt route returns 502 and the UI offers Retry or "Enter items manually"; type-to-add retries once, then shows "Couldn't read that — try again" with "or fill in the form". Core expense tracking never depends on Gemini.

Likely follow-upDid you actually test the database-down case?

Yes, AC-44. I ran the production build locally with SUPABASE_URL pointed at https://invalid.example for that one process and got 503 {"ok":false}; the normal environment returns 200.

Q131What if Frankfurter is down?

SaygetRate tries the fx_rates cache for that date first. On a miss it calls Frankfurter with a 5 s timeout, and if that fails it returns RATE_UNAVAILABLE. The form then asks for a manual rate, which is stored with fx_source = manual (R18, AC-7). INR expenses in an INR group never need a rate.

Likely follow-upAnd the demo's USD expense?

It uses a fixed rate in the seed (95.98), so creating a demo never makes an external call.

Q132What if the keep-alive stops running?

SayThe Supabase free project would pause after about 7 idle days and the app would fail until it's restored. GitHub can delay schedules, and disables scheduled workflows after 60 days of repo inactivity (risk K5). The fix is to re-enable the workflow and run it manually. The plan says to do that the day before grading.

Likely follow-upHow would you know it stopped?

The workflow fails loudly (curl --fail). For a real service I'd add an uptime monitor that alerts me, not just a ping.

Q133What if two people edit the same expense at the same time?

SayLast write wins (a stated non-goal, risk K8). Each update is atomic, so the expense is always internally consistent: payers and splits sum to the total. Both edits appear in the activity log with before and after values, so people can see what happened.

Likely follow-upCould balances become inconsistent?

No. Balances are always recomputed from the stored expenses, and every expense individually satisfies the invariants checked in SQL.

Q134What if a request dies halfway through a write?

SayEvery multi-row write is one Postgres function call, which is one transaction: the expense row, the payer and split rows, the invariant check and the activity entry commit together or not at all. The client just sees an error and can retry with its input still in the form.

Likely follow-upIs retrying safe, or could it double-create?

A retried create could create a second expense if the first actually committed and only the response was lost. Idempotency keys would fix that; it's on my list.

Q135What if a function times out on Vercel during a receipt scan?

SayThe Gemini call has a 25 s timeout inside a route allowed 60 s (maxDuration), so Quits returns a clean 502 "Couldn't read this receipt" long before Vercel would kill it. The user can Retry or enter the items manually.

Likely follow-upWhy 25 s?

Long enough for a big receipt most of the time; the Phase 1 test required JSON in under 20 s on a real bill. It's short enough that the user isn't stuck, and it fits safely in the route's budget (risk K4).

Q153What are the ethical issues in this app?

Q154How did you handle personal data in the eval receipts?

Trade-offs and alternatives (why not X?) 7

Q157Why not Firebase/Firestore?

SayA ledger is relational and invariant-heavy: payers, splits and settlements referencing members, sums that must match, unique names, and soft deletes. Postgres gives constraints, foreign keys and multi-row transactions in functions, so "Σ payers = Σ splits = total" can be enforced in the database itself. Firestore would push all of that into application code.

Likely follow-upWhat does Supabase give you beyond Postgres?

Hosting, the HTTP API and the CLI for migrations. I deliberately don't use its browser client or auth.

Q158Why Gemini instead of OCR like Tesseract?

SayReceipts aren't just text; you need structure: which line is an item, which is tax, whether an add-on belongs to an item, whether the total is after a coupon. A vision LLM with a JSON schema handles that layout reasoning directly, and its output is validated by zod and reviewed by the user anyway. OCR plus hand-written rules would break on every new bill format.

Likely follow-upWhy flash-lite rather than a bigger model?

Free-tier availability, speed and cost. The eval shows answered receipts read perfectly; the failures were timeouts and capacity, not reading quality.

Q159Why not integer linear programming for minimum payments?

SayILP would work and scales further with a good solver, but it adds a heavy dependency and is harder to prove and test. The subset DP is about 60 lines, exact up to 18 people, deterministic, and verified against brute force. For student groups that's the better trade-off.

Likely follow-upWhen would you switch?

If real groups regularly had more than 18 people with nonzero balances. Then greedy's approximation might cost noticeably more payments.

Q160Why not real-time updates with WebSockets?

SayIt's a non-goal for the build budget. Also, the browser never talks to Supabase directly, so Supabase Realtime in the browser would break my security model. Refreshing shows other people's changes, which is fine for an expense log.

Likely follow-upHow would you add it safely?

Server-sent events or short polling from my own server, which checks the token, rather than giving the browser a database connection.

Q161Why not a cron job for recurring expenses?

SayVercel Cron and server-side schedulers were made non-goals in v0.2. Lazy generation on group open needs no scheduler, can't miss runs, and dates each expense on its occurrence date, so balances are right whenever anyone looks. The unique (rule, occurrence) constraint prevents duplicates.

Likely follow-upDownside?

Nobody gets a notification when rent is "added", and an occurrence appears in the list only once someone opens the group (risk K13, accepted).

Q162Why store money in paise instead of rupees with decimals?

SayIntegers make the sums exact and the invariants checkable with equality. Decimal types would work in the database, but the JavaScript side would still need careful handling. One representation, minor units everywhere, with BigInt for products, is the simplest correct design.

Likely follow-upWhat about currencies like JPY?

Each currency has an exponent: JPY's is 0, so its minor unit is one yen. The conversion formula scales by 10^(exp_base − exp_src).

Q163Why not let the browser call Supabase with RLS policies, as Supabase intends?

SayRLS policies need an identity to check (auth.uid()), and Quits deliberately has no accounts. Writing policies around a link token would be complex and error-prone. Keeping all access server-side means the browser holds no database key, and authorization is a simple, testable rule: you need the token, and ids must belong to that group.

Likely follow-upWhat's the cost of that choice?

Every request goes through my server, so no direct-from-browser realtime or storage, and the server is a single point of authorization that must be right. It's tested by the cross-group DB tests.

Walk me through this code 8

Q164Walk me through greedy() in lib/simplify.ts.

SayIt copies the balances and checks they sum to zero, otherwise it throws. Then it loops: it scans for the most negative balance (the debtor) and the most positive (the creditor), ties going to the lower index, which is member order. If either is missing, it stops. Otherwise x = min(−debtor, creditor), it records the payment debtor → creditor of x, and adjusts both balances. Each iteration zeroes at least one person, so it terminates within n − 1 payments.

Likely follow-upIts complexity?

O(n) per iteration × at most n iterations = O(n²), which is trivial for 50 members.

Q165Walk me through maxZeroSumPartition().

SayIt refuses n > 18. It allocates sums (Float64Array) and dp (Int32Array) of size 2ⁿ. For every mask, it takes the lowest set bit with mask & −mask and finds its index with 31 − clz32. sums[mask] is the sum without that member plus its value. dp[mask] is the best dp of the mask minus any one member, plus 1 if sums[mask] is 0. Then recovery walks back from the full mask, always removing the lowest index that keeps dp optimal, and closes a group each time the remaining mask sums to zero. Finally it sorts the groups.

Likely follow-upWhy mask & −mask?

In two's complement, it isolates the lowest set bit. That's a cheap way to build each subset's sum from a smaller subset already computed.

Q166Walk me through allocate() in lib/money.ts.

SayIt asserts the total is a safe integer and the weights aren't empty. A negative total is allocated as positive and negated. Weights become BigInt, must be non-negative and must not sum to zero. floors = total × w ÷ Σw, rems = total × w mod Σw, leftover = total − Σfloors. Indices are sorted by remainder descending, ties by index ascending, and the first leftover indices get +1. It returns the numbers.

Likely follow-upWhy sort ties by index?

Callers pass people in member order, so ties go to the earlier member, which gives deterministic results that tests can pin, like [3334, 3333, 3333].

Q167Walk me through createParseHandler().

SayIt's a factory that takes the dependencies and returns handle(request, token). It finds the group (404), parses the body with zod (400), keeps active members, checks that "me" is one of them (404), and bumps the limits (429). It builds the request from NL_PROMPT, nlUserText and NL_JSON_SCHEMA and an AbortController. attempt() calls the model; on an error it records the HTTP status, waits about 1 s and retries once, unless the deadline has passed. Promise.race against a 20 s timer either times out (502 timeout) or gets text, which goes through parseNlModel (502 invalid_output) and resolveNl, returning 200 {prefill, flags}.

Likely follow-upWhy a factory?

Dependency injection: the production wiring passes the real database and Gemini; tests pass fakes. The same code runs in the eval harness too.

Q168Walk me through the receipt extract route.

Sayawait connection() keeps it dynamic. Resolve the group (404). Reject a declared Content-Length over 1 MB plus 64 KB of headroom (413). Read the form data, get the image Blob (400 if missing), check the size again (413), sniff the magic bytes (415), bump the scan limits (429). Then call extractReceipt with the base64 image and the group's base currency as the fallback currency. On failure, log only the reason and return 502. On success, store a draft with the model name and parsed output, and return the receiptId and latency.

Likely follow-upWhy check the size twice?

The header check rejects huge uploads before reading the body. The blob check catches a missing or false Content-Length.

Q169Walk me through buildUpiLink().

SayIt URI-encodes pa and puts "@" back (%40 → @), URI-encodes pn, formats the amount with exactly 2 decimals using minorToMajorString (45050 → "450.50"), and builds tn = "Quits: {group}" cut to 50 characters and encoded. Result: upi://pay?pa=…&pn=…&am=…&cu=INR&tn=…. AC-13 pins the exact output string.

Likely follow-upWhy keep @ literal?

SPEC §4.3 specifies it; UPI apps expect a readable VPA in pa.

Q170Walk me through how 'Your groups' records a visit.

SayWhen a group page loads and the device's identity is known, IdentityProvider calls updateRecent with recordVisit(list, {token, name, memberName, demo}, now). recordVisit validates the entry, updates the name, member, demo flag and time, clears "unavailable", moves it to the top, then normalize() sorts newest first, removes duplicates by token and caps the list at 20. saveRecent writes JSON to localStorage inside try/catch, and listeners re-render the home list.

Likely follow-upWhat if localStorage contains garbage?

parseRecent never throws. Non-JSON gives an empty list, and wrongly shaped entries are dropped individually; even the pre-v1.3 shape {token, name, openedAt} is accepted. Fourteen unit tests cover this.

Q171Walk me through the theme script and why it's inline.

SayTHEME_INIT_SCRIPT is a small IIFE in head. It defaults to "dark", tries localStorage.getItem("quits:theme"), accepts only dark, light or system, and sets data-theme on html. It runs before the first paint, so a light-theme user never sees a dark flash. It's the only raw HTML in the app, and it's a constant string with no user input. A unit test runs it against fake document and storage objects, including storage that throws.

Likely follow-upWhy suppressHydrationWarning on html?

The server renders data-theme="dark", and the script may change it before React hydrates. That mismatch is expected and harmless, so the warning is suppressed for that one attribute.
